# text_summarization

Абстрактивная суммаризация длинных текстов через seq2seq-модель (по умолчанию `IlyaGusev/rut5_base_sum_gazeta`). Модуль строит два варианта результирующего датасета: с заменой текста на суммаризацию и с конкатенацией оригинала и суммаризации через разделитель. Используется как препроцессор для классификаторов: позволяет проверить, насколько модель полагается на длинный контекст и насколько — на «главную мысль».

## Как это работает

### Постановка задачи

Длинные тексты (юридические документы, статьи) часто не помещаются в окно энкодера: даже у `xlm-roberta-base` лимит — 512 токенов, а наши тексты после токенизации легко превышают 2000. В модуле `bert_embeddings`/`bert_classification` проблема решается чанкованием с усреднением, но это даёт «размазанную» репрезентацию. Альтернативный путь — сжать текст до краткой выжимки **до** эмбеддинга:

1. Если суммаризатор хорошо находит главную мысль, то на компактном входе классификатор работает быстрее и порой точнее.
2. Если оригинал важнее (например, конкретные термины), то суммаризация может потерять сигнал.

Чтобы проверить оба сценария, модуль одновременно строит две версии датасета — заменённую и комбинированную. Обе подаются в downstream-классификатор отдельно и сравниваются по метрикам.

### Архитектура

```
input.csv ──► load_dataset ──► reset_index + sample_id
                                       │
                                       ▼
                     ┌─────────────────────────────────────┐
                     │ tokenizer.encode (truncation=True) │
                     │ model.generate (beam search)       │
                     │ tokenizer.batch_decode             │
                     └─────────────────────────────────────┘
                                       │
                          summaries: list[str], len == len(df)
                                       │
                ┌──────────────────────┴────────────────────────┐
                ▼                                               ▼
       build_summarized_dataset                      build_combined_dataset
       (text ← summary)                              (text ← orig + [SEP] + summary)
                │                                               │
                ▼                                               ▼
       <stem>_summarized.<ext>                  <stem>_original_plus_summary.<ext>
```

Все этапы — однопроходные. Модель загружается один раз, тексты идут батчами через `summarize_dataframe`, который сохраняет позиционное соответствие `summaries[i] ↔ df.iloc[i]`. Никакой записи в исходный CSV: оба выхода кладутся в `output_dir`.

### Модель — rut5_base_sum_gazeta

По умолчанию используется `IlyaGusev/rut5_base_sum_gazeta` — русскоязычная T5-base, дообученная на корпусе новостей «Газета.Ru». Это encoder-decoder: энкодер читает входной текст, декодер авторегрессивно генерирует выжимку токен за токеном.

Альтернативы (закомментированы в `config.py`):
- `IlyaGusev/mbart_ru_sum_gazeta` — mBART, поднимает окно до 1024 токенов;
- `d0rj/rut5-base-summ` — другая T5-вариация для русского.

Модель переводится в `eval()`, размещается на CUDA → MPS → CPU (в порядке доступности) и используется в режиме `torch.no_grad()` — никакого обучения, только инференс.

### Усечение входа

T5-модели обучены на ограниченном окне (для `rut5_base_sum_gazeta` — порядка 512–1024 токенов). Если подать больше, генерация ломается. Поэтому вход усекается через `truncation=True, max_length=effective_max_input`.

Эффективный лимит вычисляется аккуратно:

```python
def _effective_max_input(tokenizer, max_input_length):
    tok_max = tokenizer.model_max_length
    if tok_max is None or tok_max > 10_000:
        return max_input_length
    return min(max_input_length, tok_max)
```

Поясняем `tok_max > 10_000`: у некоторых токенизаторов `model_max_length` хранит «сторожевое» значение около `10^30` — это означает «без ограничения». В таком случае надо использовать пользовательский лимит, а не `min` с астрономическим числом (это просто вернёт `max_input_length`, но проверка делает намерение явным).

Дефолт `MAX_INPUT_LENGTH=600` — компромисс между потерей контекста и качеством генерации. На 512 модель работает гарантированно, на 600 — на грани, но обычно стабильно (по факту для T5 это soft-cap, обусловленный позиционными эмбеддингами).

### Генерация суммаризации

Используется `model.generate(...)` с beam search:

```python
model.generate(
    **inputs,
    max_new_tokens=128,         # MAX_SUMMARY_LENGTH
    min_new_tokens=30,          # MIN_SUMMARY_LENGTH
    num_beams=4,
    early_stopping=True,
    no_repeat_ngram_size=3,
)
```

Разбор параметров:

**`num_beams=4`** — beam search с 4 параллельными гипотезами. На каждом шаге декодер раздувает каждую гипотезу до vocab_size продолжений, оставляет top-4 по совокупной log-вероятности. Greedy decoding (beams=1) даёт более «плоские», часто повторяющиеся выжимки; 4 — стандартный компромисс для суммаризации (8 уже почти не улучшает, но в 2× медленнее).

**`max_new_tokens=128, min_new_tokens=30`** — жёсткие границы длины суммаризации. Контролируем именно «новые» токены (выход декодера), а не общую длину (для encoder-decoder важно). Слишком короткий минимум приводит к выжимкам в одну фразу — теряется смысл; слишком длинный максимум — модель начинает копировать оригинал.

**`early_stopping=True`** — beam search завершается, как только лучшие гипотезы сошлись (все beams выдают EOS). Без этого генерация продолжается до `max_new_tokens` даже если завершённая фраза уже найдена.

**`no_repeat_ngram_size=3`** — на каждом шаге декодер штрафует продолжения, которые создали бы 3-грамму, уже встречавшуюся в текущей гипотезе. Боремся с типичной проблемой авторегрессивных моделей — «зацикливанием» на одной фразе («Суд постановил, суд постановил, суд постановил…»). Размер 3 — достаточно строго, но не блокирует естественные повторы коротких слов («в», «на», «и»).

`torch.no_grad()` оборачивает вызов: градиенты не считаются, активации не сохраняются — экономия памяти и ускорение в ≈1.5×.

### Пакетная обработка с сохранением позиций

`summarize_dataframe` — главная пакетная функция. Алгоритм:

1. **Очередь непустых текстов**:
   - Проходим `df[text_column]`, пропускаем `None`, NaN (`isinstance(t, float) and pd.isna(t)`), пустые строки после `strip()`.
   - Кладём в `queue_texts` сам текст, в `queue_positions` — индекс в исходном DataFrame.
   - Заранее аллоцируем `out = [""] * len(raw_texts)` — все позиции начинаются с пустой строки.

2. **Батчевая суммаризация**:
   - Идём по очереди срезами по `batch_size`.
   - Для каждого среза вызываем `summarize_batch` → получаем `len(batch)` суммаризаций.
   - Раскладываем результаты обратно в `out` по `queue_positions[start:start+batch_size]`.

3. **Возврат**: `out` — список длины `len(df)`. Пустые/NaN остались пустыми строками, все остальные позиции — реальные суммаризации.

Зачем такая схема, а не простое «итерируем все строки и подаём в модель»: модель плохо работает на пустых/мусорных входах (может зависнуть на padding или сгенерировать «галлюцинацию» из decoder_start_token). Отфильтровать заранее проще, чем разбираться с пограничными случаями внутри генерации. И позиционное соответствие `summaries[i] ↔ df.iloc[i]` критично — иначе при последующей сборке датасета метки уедут относительно текстов.

### Два варианта выходного датасета

После получения списка `summaries` модуль строит две версии:

**1. Заменённый (`build_summarized_dataset`)**:

```
text_orig → summary
label → label  (без изменений)
```

Колонка `text` физически заменяется суммаризацией. Все остальные колонки (включая `label`, `sample_id`) сохраняются. Это «короткий» датасет — компактный, теряет детали, но содержит главную мысль.

**2. Комбинированный (`build_combined_dataset`)**:

```
text_orig → orig + " [SEP] " + summary
label → label
```

Конкатенация через `SEPARATOR = " [SEP] "` (пробелы по краям важны — нужны для токенизации, чтобы `[SEP]` не приклеился к соседнему слову). У токенизаторов `[SEP]` обычно — реальный спец-токен, поэтому он будет правильно распознан. Но даже если нет (например, T5 не имеет `[SEP]`) — это всё равно стабильный текстовый маркер, который классификатор может выучить как «граница».

Этот вариант не теряет оригинал и одновременно явно подсвечивает выжимку — гипотеза в том, что классификатор может опираться и на главную мысль (короткая часть после `[SEP]`), и на детали (длинная часть до).

### Поддержка форматов входа/выхода

`load_dataset` и `save_dataset` определяют формат по расширению:

| Расширение | Read | Write |
| --- | --- | --- |
| `.csv` | `pd.read_csv` | `to_csv(index=False)` |
| `.json` | `pd.read_json(lines=False)` | `to_json(orient="records", force_ascii=False, indent=2)` |
| `.jsonl` | `pd.read_json(lines=True)` | `to_json(orient="records", lines=True, force_ascii=False)` |

`force_ascii=False` — критично для русского: без него кириллица сериализуется как `\u0436\u0438\u0432\u043e\u0439` и файл становится нечитаемым глазами.

### Производные пути

`derive_output_paths(input_path, output_dir)` детерминированно формирует имена выходов от stem входа:

```
data/train_augmented.csv
    → <output_dir>/train_augmented_summarized.csv
    → <output_dir>/train_augmented_original_plus_summary.csv
```

Расширение сохраняется — формат входа определяет формат выхода. `output_dir` создаётся через `os.makedirs(parent, exist_ok=True)`.

### Поле `sample_id`

После `reset_index(drop=True)` модуль добавляет колонку `sample_id = df.index`. Это техническая идентификация исходной позиции — полезно, если потом два датасета (суммаризированный и комбинированный) объединяются по сэмплам или сопоставляются с метриками классификатора по строкам. Колонка переносится в оба выхода как обычная.

### Сохранение результатов

После генерации сохраняются ровно два файла рядом:

```
output_dir/
├── <stem>_summarized.<ext>             # текст = суммаризация
└── <stem>_original_plus_summary.<ext>  # текст = оригинал [SEP] суммаризация
```

Если входной CSV содержал 1000 строк, оба выхода тоже содержат 1000 строк (включая исходно пустые — с пустой суммаризацией). Это важно для downstream-классификатора: соответствие строк по индексу сохраняется.

## Структура модуля

| Файл | Содержимое |
| --- | --- |
| `config.py` | Модель, имена колонок, лимиты длины, batch_size, разделитель. |
| `model.py` | `load_summarization_model`, `_detect_device` (CUDA → MPS → CPU). |
| `data.py` | Загрузка/сохранение датасетов, сборка двух выходных версий, формирование путей. |
| `summarize.py` | `summarize_batch` (один батч через generate) и `summarize_dataframe` (всё в порядке позиций). |
| `main.py` | CLI: парсинг аргументов, оркестрация всего пайплайна. |
| `__init__.py` | Реэкспорт `run`. |

## CLI

Минимальный запуск:

```bash
python -m text_summarization.main \
    --input-path data/train.csv \
    --output-dir runs/summarization
```

С переопределением модели и параметров генерации:

```bash
python -m text_summarization.main \
    --input-path data/train_augmented.jsonl \
    --output-dir runs/summarization_v2 \
    --model-name IlyaGusev/mbart_ru_sum_gazeta \
    --max-input-length 1024 \
    --max-summary-length 200 \
    --min-summary-length 50 \
    --batch-size 4
```

С нестандартным разделителем:

```bash
python -m text_summarization.main \
    --input-path data/train.csv \
    --output-dir runs/summ \
    --separator " ||| "
```

from text_summarization.main import run

## Входы

| Колонка | Тип | Обязательность | Комментарий |
| --- | --- | --- | --- |
| `text` (`--text-column`) | str | да | Текст для суммаризации. NaN/пусто → пустая суммаризация. |
| `label` (`--label-column`) | str | нет | Не используется внутри, переносится как есть. |
| прочие колонки | любые | нет | Переносятся в оба выхода без изменений. |

Поддерживаемые форматы: `.csv`, `.json`, `.jsonl`.

## Выходы

| Файл | Описание |
| --- | --- |
| `<stem>_summarized.<ext>` | Колонка `text` заменена суммаризацией. Все прочие колонки сохранены. |
| `<stem>_original_plus_summary.<ext>` | Колонка `text` = `orig + separator + summary`. |

Обе версии имеют ту же длину, что и вход; добавляется колонка `sample_id`.

## Ключевые параметры

| Параметр | Дефолт | Назначение |
| --- | --- | --- |
| `SUMMARIZATION_MODEL` | `IlyaGusev/rut5_base_sum_gazeta` | Идентификатор модели на HuggingFace Hub. |
| `TEXT_COLUMN` | `"text"` | Имя колонки с текстом. |
| `LABEL_COLUMN` | `"label"` | Имя колонки с меткой (переносится). |
| `MAX_INPUT_LENGTH` | 600 | Лимит входа в токенах (с учётом `tokenizer.model_max_length`). |
| `MAX_SUMMARY_LENGTH` | 128 | `max_new_tokens` в `generate`. |
| `MIN_SUMMARY_LENGTH` | 30 | `min_new_tokens` в `generate`. |
| `BATCH_SIZE` | 8 | Размер батча для генерации. |
| `SEPARATOR` | `" [SEP] "` | Разделитель в комбинированном датасете. |

Параметры beam search (`num_beams=4`, `no_repeat_ngram_size=3`, `early_stopping=True`) зашиты в `summarize_batch` и не выведены в CLI — это разумные дефолты для русскоязычной T5.

## Метрики

Сам модуль не вычисляет метрики качества суммаризации — это инфраструктурный шаг. Качество оценивается косвенно: после суммаризации оба варианта датасета подаются в downstream-классификатор (`bert_classification` / `hybrid` / `cosine_similarity_classification`), и сравниваются `balanced_accuracy` / `macro_f1` с теми же метриками на оригинальном датасете.

Гипотеза эксперимента:

- **`_summarized` обходит оригинал** → классификатору достаточно главной мысли, длинный контекст шумит.
- **`_original_plus_summary` обходит оригинал** → суммаризация помогает как «attention prior», но детали важны.
- **Оригинал обходит оба** → суммаризатор теряет специфический сигнал (термины, числа, имена сторон) — суммаризация не полезна.

Какой результат истинен — определяется на конкретном корпусе и в этом модуле не предрешается.
